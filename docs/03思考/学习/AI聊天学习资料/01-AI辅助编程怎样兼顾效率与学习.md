# AI 辅助编程怎样兼顾效率与学习

## 真正的问题不是“代码由谁写”

讨论 AI 编程时，很容易把方法排成一条简单的优劣链：纯手写最好，让 AI 给小段代码次之，Vibe Coding 最差。

这个排序太粗了。敲键盘不是学习的核心，生成代码的长度也不是决定因素。更重要的问题是：程序从想法变成运行结果的过程中，哪些关键判断发生在你的脑子里，哪些被交给了模型？

一项编程任务通常包含这条链：

`目标 → 问题分解 → 模块与接口 → 具体实现 → 预测结果 → 运行验证 → 根据反馈修改`

如果 AI 只帮助查询语法和 API，而目标、分解、接口、预测和验证仍由你主导，你依然在训练编程能力。反过来，即使 AI 每次只给十行代码，如果你始终是“复制 → 运行成功 → 下一段”，也只是把一次完整生成拆成了许多次慢速生成。

## 编程中有三层决策

可以把任务里的决策大致分成三层。

### 1. 分解

大问题应该拆成哪些小问题？每一步先解决什么？

例如做一个 Chrome 扩展时，不能只停留在“帮我修改发送内容”。需要继续拆成：

- 用户指令从哪里输入？
- 指令保存在哪里？
- 页面脚本什么时候读取它？
- 用户点击发送时，怎样组合指令和问题？
- 页面怎样感知输入框已经改变？

### 2. 接口

每个模块接收什么、输出什么，数据怎样穿过模块？

例如：

`popup 输入 → chrome.storage → content script → 用户问题 + 指令 → 输入框`

接口决策迫使你理解变量、状态、调用顺序和数据流。这些通常比记住某个 API 名字更接近可迁移的编程能力。

### 3. 实现

模块内部具体使用哪个函数、参数怎样写、配置文件采用什么格式。

这一层有很多适合交给 AI 辅助查询的内容。忘记 `addEventListener` 的参数，不等于不理解事件监听；查文档或问 AI 都是合理的信息检索。

## 三种协作模式的差别

### 完全手写

优点是所有决策都由自己经历。风险是把大量时间耗在语法回忆和资料检索上，产生的困难未必都有学习价值。

如果你已经知道需要监听点击事件，只是忘了 API 名称，长时间盯着空白编辑器并不会自动带来更深的理解。

### 小步协作

你负责拆问题、确定数据流和模块边界，AI 提供当前最小实现、语法解释或候选方案。代码被接入项目时，你还要处理参数、状态和调用顺序。

这种方式通常更适合学习，但前提不是“代码块足够短”，而是每个代码块仍在你的理解边界内。

### Vibe Coding 或高度 Agent 化开发

你描述目标，模型负责拆解、设计、编码、调试甚至验收。它能显著提高交付速度，但很容易让学习者只保留最高层的需求，而失去程序形成过程。

这不意味着它永远不好。生产项目的目标可能是稳定交付，而不是训练基础能力。此时可以外包更多实现，但要用 Git、测试、日志、验收标准和文档约束风险。问题在于：不要把“交付效率高”误认为“学习效率高”。

## 一个更适合学习的循环

### 1. 先说清当前最小目标

不要一次提出整个项目。明确这一轮只改变什么，以及成功时能观察到什么。

### 2. 在看到答案前先做预测

哪怕预测不完整，也先回答：

- 可能需要监听什么事件？
- 数据从哪里来、到哪里去？
- 应该改哪个模块？
- 哪一步最可能出错？

错误预测并不是失败，它会暴露你的因果模型缺在哪里。

### 3. 让 AI 只补当前缺口

可以问 API、语法、最小示例或两种方案的区别。尽量避免一句话把需求、设计、实现和调试全部外包。

### 4. 解释代码，而不是只运行代码

接入前至少能说清：

- 输入是什么？
- 输出或副作用是什么？
- 为什么放在这里？
- 它依赖什么状态？

### 5. 运行前预测，运行后对照

理解最可靠的表现之一，是能够预测变化。

例如看到：

```js
document.addEventListener("click", handler);
```

可以继续问：

- 把 `click` 改成 `keydown` 会发生什么？
- 把 `document` 改成某个按钮会发生什么？
- 为什么点击子元素时，`document` 也可能收到事件？

### 6. 做一个小变体

改事件类型、目标元素、参数或数据来源，再预测结果。变体能检验你理解的是机制，还是只记住了当前答案。

### 7. 脱离答案复述

不看代码，重新说出整体流程；或者隔一段时间自己完成同类的小任务。

## 怎样判断自己正在学习，还是只在拼接

可以用四个问题快速检查：

1. 我能解释为什么现在要写这段代码吗？
2. 我能说出它与前后模块怎样连接吗？
3. 改一个关键参数后，我能预测大致结果吗？
4. 出错时，我知道先观察哪一层吗？

如果四个问题大多答不上来，就应该缩小 AI 输出的粒度，或者先回到数据流和机制，而不是继续索取下一段代码。

## 最后留下的原则

AI 最适合帮你跨过“我知道要做什么，但不知道具体怎么写”。

它不应该长期替你跨过“我不知道为什么要这样做”。

学习阶段要守住的不是代码所有权，而是问题分解、接口判断、结果预测和验证解释的主导权。
