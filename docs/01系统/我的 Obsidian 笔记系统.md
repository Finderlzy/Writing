这套笔记系统的目标不是把所有知识整理得像一本教科书，而是让 Obsidian 真正成为我的思考工具。

我需要它完成几件事：记录正在发生的思考，保留思考过程，把值得长期使用的认识抽出来，在未来重新找到这些东西，同时又不让整理笔记本身成为负担。

因此，笔记不再主要按照“Java、前端、投资、动漫、写作”这样的领域划分，而是按照**一篇笔记在我的思考中承担什么作用**来划分。

当前结构为：

```text
00收集/
01系统/
02主线/
03概念/
04项目/
05碎碎念/
09附件/

index.md
```

一级目录只表达笔记承担的职责，不预先固定所有分类。以后可以在 `docs/` 下自由新增分类目录；`09附件/` 专门保存图片、PDF 等附件，不能把普通笔记放进去。

## 00收集

收集目录只负责一件事：**先把东西记下来。**

突然产生一个问题、一个灵感、一段还没想清楚的想法时，不需要立刻判断它属于哪个领域，也不用考虑最终应该放在哪里，直接写进收件箱。

例如：

```text
为什么 Java 数组可以动态确定长度
AI 协作编程是不是改变了“编程”的含义
突然想到的一种小说设定
为什么我最近一直想优化学习方法
```

收集目录不是长期存储区域，而是一个缓冲区。

之后再根据这篇笔记的发展决定：

- 如果形成了一条持续探索的问题，进入“02主线”；
    
- 如果提炼出了可以反复使用的认识，进入“03概念”；
    
- 如果只是一次个人想法，可以进入“05碎碎念”；
    
- 如果开始围绕某个明确成果行动，则进入“04项目”。
    

记录时优先保证思考不中断，而不是保证分类正确。

## 01系统

这里存放的是笔记系统本身的规则和工具。

例如：

```text
系统/
    笔记系统说明.md
    笔记样式规范.md
    主线模板.md
    概念模板.md
    项目模板.md
```

以后有关：

```text
Obsidian 配置
插件配置
标签规范
属性规范
模板
```

也可以进入这里。

它相当于整个知识库的说明书。

## 02主线

主线保存的是：

> **我正在持续理解什么问题，以及我是怎么一步步理解它的。**

它是整个系统里最重要的部分。

例如：

```text
Chrome 插件开发学习
Java 基础学习
MySQL 学习
长期投资学习
大学学习方式探索
AI 协作编程方式思考
理解计算机网络
```

主线不是整理好的教材，也不要求干净。

里面可以出现：

- 我最开始的猜测；
    
- 写错的代码；
    
- 遇到的问题；
    
- GPT 或老师的解释；
    
- 我的反驳；
    
- 后来修改的理解；
    
- 截图；
    
- 实验结果；
    
- 新产生的问题。
    

主线真正保存的是**知识形成的过程**。

例如学习 Chrome 插件时：

```markdown
# Chrome 插件开发学习 1

我现在想监听 DeepSeek 的输入框。

问题变成了：怎么找到网页中的输入框？

这里接触到了 [[DOM]]。

后来我发现可以监听 input、keydown 等事件。

那么问题又变成了：浏览器里的“事件”到底是什么？

→ [[DOM事件]]

监听发送按钮的时候，又遇到了事件传播的问题。

→ [[事件传播]]
```

主线允许不断产生支线，但重要的支线不会无限展开，而是逐渐抽成独立的概念笔记。

因此：

> 主线保存时间顺序，概念保存逻辑结构。

---

## 03概念

概念保存的是：

> **脱离当前上下文以后，未来依然值得再次使用的认识。**

这里的“概念”是广义的，不只是课本上的术语。

例如编程领域：

```text
DOM
事件传播
封装
HTTP
DNS
回调函数
依赖注入
```

学习领域：

```text
主动回忆
认知负荷
知识迁移
反馈
```

投资领域：

```text
机会成本
折现率
复利
风险溢价
```

写作领域：

```text
留白
人物关系
叙事视角
```

甚至一个并没有标准名称、但我发现自己反复使用的思维模型，也可以成为概念。

概念笔记不需要按领域分文件夹。

例如不需要：

```text
编程概念/
学习概念/
投资概念/
```

因为同一个概念可能跨越多个领域。

例如“反馈回路”可以同时出现在：

```text
编程调试
学习
内容创作
项目开发
```

如果一开始按照学科把它们隔开，反而会失去这种连接。

一篇概念笔记可以大致包含：

```markdown
# 事件传播

## 它是什么

……

## 为什么需要它

……

## 它是怎么工作的

……

## 我在哪里遇到过

[[Chrome插件开发学习1]]

第一次监听发送按钮时遇到。

[[Obsidian插件开发学习]]

后来再次遇到同样的问题。

## 相关概念

[[DOM]]
[[事件监听]]
[[事件委托]]
```

其中“我在哪里遇到过”很重要。

我不是在写百科全书，而是在逐渐建立：

> **概念 ↔ 自己真实经历**

之间的连接。

不过，并不是每学到一个新东西都必须创建概念笔记。

判断标准是：

> **这个东西以后是否值得再次引用？**

如果只是某个 API 的一个小参数，可能留在主线里就够了。

如果它能够解释很多现象，或者之后很可能再次遇到，就值得抽出来。

## 04项目

项目保存的是：

> **我正在试图真正做成什么。**

主线和项目最容易混淆。

判断方式很简单：

> 主线的核心是“我要理解什么”。

> 项目的核心是“我要做出什么”。

例如：

```text
学习 Chrome 插件开发
```

属于主线。

而：

```text
做一个 DeepSeek 个性化 Chrome 插件
```

属于项目。

项目中存放的是**只对这个项目本身有意义的信息**，例如：

- 项目目标；
    
- 需求；
    
- 功能设计；
    
- 技术决策；
    
- 开发计划；
    
- 当前状态；
    
- Agent Plan；
    
- 验收记录；
    
- 项目复盘。
    

例如：

```text
项目/
    DeepSeek个性化插件/
        项目主页.md
        需求.md
        架构设计.md
        Agent开发Plan.md
```

但不需要一开始就创建这么多文件。

一个刚开始的项目只需要：

```markdown
# DeepSeek 个性化插件

## 为什么要做

DeepSeek 网页端没有类似 ChatGPT 的个性化指令功能。

## 想实现什么

用户可以保存自己的个性化指令。

发送消息时，插件根据情况自动加入这些指令。

## 当前状态

正在学习 Chrome 插件开发。

相关主线：

[[Chrome插件开发学习1]]

## 当前涉及的概念

[[DOM]]
[[事件监听]]
[[Chrome Content Script]]

## 下一步

完成最基本的输入框监听。
```

等项目复杂起来，再自然拆出：

```text
需求.md
设计.md
开发记录.md
验收记录.md
```

而不是提前为了“结构完整”创建一堆空文件。

项目本身也不应该变成新的知识库。

例如：

```text
事件传播是什么
```

应该进入：

```text
概念/事件传播.md
```

学习它的过程应该进入：

```text
主线/Chrome插件开发学习/
```

只有：

```text
这个项目为什么决定使用这种事件监听方式
```

这样的内容才属于项目。

同一个东西因此可以形成这样的关系：

```text
[[事件传播]]
      ↑
      │
[[Chrome插件开发学习]]
      ↑
      │
[[DeepSeek个性化插件]]
```

三篇笔记不是重复，而是在回答不同问题：

```text
概念：这是什么？

主线：我是怎么理解它的？

项目：我要怎么利用它做出东西？
```

## 05碎碎念

碎碎念保存的是：

> **我对于自己、世界、作品和经历产生的各种想法。**

它不是“作品库”。

写进这里的东西不需要完成，也不需要成熟，更不需要达到可以发布的程度。

它可以是一篇比较完整的文章，也可以只是某个晚上突然产生的一些想法。

目前的子目录可以继续保留：

```text
05碎碎念/
    二次元/
        追番/
    灵感/
    世界/
    随笔/
    学习/
    自己/
```

这里和主线有一个重要区别。

主线通常围绕：

> **我想持续搞清楚一个问题。**

碎碎念则更像：

> **我现在产生了一个想法，我想把它留下来。**

例如：

```text
看完某一集动画后的感受
突然想到自己为什么害怕平庸
一次旅行留下的印象
对朋友关系的一次思考
某天关于时间的感受
```

有些碎碎念以后可能继续发展成主线，也可能被整理、修改后成为真正的文章。

但没有必要提前给它定义成“作品”。

“是否是作品”可以以后通过状态表达，而不是靠文件夹决定。

---

## 领域不再作为主要文件夹

编程、投资、学习、写作、动漫这些领域依然有意义。

但它们不再决定文件放在哪里。

因为一篇笔记完全可能同时涉及：

```text
AI
编程
学习方法
软件工程
```

如果强迫它只能进入一个领域文件夹，就必须不断纠结：

> 它到底算哪一类？

更合适的办法是让“领域”成为属性。

例如：

```yaml
---
type: concept
domain:
  - 编程
  - 浏览器
---
```

或者：

```yaml
---
type: mainline
domain:
  - AI
  - 编程
  - 学习
---
```

这样以后可以从“编程”这个视角看到所有相关：

```text
主线
概念
项目
碎碎念
```

“编程”因此只是一个观察知识库的角度，而不是一个装文件的盒子。

---

## 分类目录如何扩展

不需要一次性整理整个知识库，也不需要为了未来可能出现的领域预先建立空目录。新笔记先进入 `00收集/`，之后根据它承担的职责移动到 `02主线/`、`03概念/`、`04项目/` 或 `05碎碎念/`。

持续学习可以在 `02主线/` 下建立 `Java学习/`、`算法学习/` 等子目录；稳定知识可以在 `03概念/` 下建立相应子目录。分类目录可以自由新增，构建程序不会读取固定分类清单。

只有少数路径属于跨工具约定：`docs/` 是内容根目录，`09附件/` 是附件目录，`00收集/` 是 Obsidian 的新笔记目录，`site/` 是发布产物目录。修改这些路径时，必须同步 `mkdocs.yml`、`docs/.obsidian/app.json`、`.gitignore` 和自动验收测试。

# 这套系统真正的运行方式

这套系统不是：

> 先设计一套完整知识体系，然后不断把知识塞进去。

而是：

```text
经历 / 学习 / 阅读 / 思考
        ↓
     收件箱
        ↓
   开始持续探索
        ↓
       主线
        ↓
发现可以反复使用的认识
        ↓
       概念
```

与此同时，另一条路径可能是：

```text
产生一个想法
    ↓
  碎碎念
```

如果决定真正把某件东西做出来：

```text
形成明确成果目标
        ↓
       项目
```

这些区域之间不是互相隔离的。

它们通过双向链接不断形成关系。

最终整个知识库会慢慢从：

> 一个按照学科摆放文件的柜子

变成：

> 一张由我的经历、思考、概念和行动共同生长出来的网络。

# 最核心的判断原则

以后不知道一篇笔记放在哪里时，只问它现在承担什么职责。

**正在持续探索一个问题：主线。**

**形成了以后还会反复使用的认识：概念。**

**只是想保存自己此刻产生的想法：碎碎念。**

**存在一个明确想做出来的成果：项目。**

**还没想清楚：收件箱。**

不要为了分类打断思考。

不要为了完整维护知识库。

不要提前建立大量空结构。

让结构随着真实的学习、思考和行动自然长出来。
