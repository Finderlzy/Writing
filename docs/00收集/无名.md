## A：保护代理不被系统强杀

1. 给 x-ui 服务加一份附加配置（不改原来的服务文件）：

```bash
mkdir -p /etc/systemd/system/x-ui.service.d
```

```bash
printf '[Service]\nOOMScoreAdjust=-900\n' > /etc/systemd/system/x-ui.service.d/oom.conf
```

2. 重新加载配置并重启 x-ui。**代理会断开几秒**，挑个不用代理的时候做：

```bash
systemctl daemon-reload
```

```bash
systemctl restart x-ui
```

3. 检查是否生效，输出 `-900` 就对了：

```bash
cat /proc/$(pgrep -f "bin/xray-linux-amd64 -c")/oom_score_adj
```

数值越低越不容易被杀。设成 -900 而不是 -1000（永不被杀），是为了万一代理自己失控，系统还能处理它。

## B：让网站的内存上限生效

```bash
cd /opt/findhot && docker compose up -d
```

不要加 `--build`，也不要加 `--profile https`。执行后会重启数据库、api、worker 和 web，网站中断一两分钟；worker 会先等手上的模型调用跑完再停，最慢 3 分半。等它跑完，用下面这条看各容器的内存，MEM USAGE 一栏会显示 `xx MiB / 256MiB` 这样的上限：

```bash
docker stats --no-stream
```

B 改了什么（配置文件也放在本机，`AIHOT/docker-compose.override.yml`，以后用 tar 上传更新时一起带上）：

| 容器 | 现在占用 | 上限 |
|---|---|---|
| worker | 约 110 MB | 384 MB |
| 数据库 | 约 75 MB | 256 MB，缓存从 128 MB 降到 64 MB（库只有 33 MB），最大连接数从 100 降到 40 |
| api | 约 20 MB | 256 MB |
| web | 约 20 MB | 192 MB |

api 和 worker 的数据库连接池也从各 10 个降到各 5 个。上限比现在的占用宽松很多，正常情况下碰不到，只用来防止某个进程失控把整台机器拖垮。哪个容器反复重启，说明它的上限太紧，告诉我再调。
