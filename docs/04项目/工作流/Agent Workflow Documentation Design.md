## 核心思想

这个 Agent 工作流的核心不是让单个 Agent 从头到尾完成整个项目，而是通过不同 Agent 分担不同认知职责，并通过文档传递项目状态，形成「规划 → 执行 → 验收 → 重新规划」的闭环。

四个 Agent 分别负责：

- Agent 1：确定项目方向，回答「做什么、为什么做」
    
- Agent 2：制定执行方案，回答「怎么做、下一步做什么」
    
- Agent 3：负责实现，回答「如何把计划变成代码」
    
- Agent 4：负责验收，回答「实现是否符合要求」
    

其中，文档 A、文档 B 和 Report 是三个核心状态文件，它们分别代表项目目标、执行计划和实际结果。

---

# 文档 A：Project Vision

## 定位

文档 A 是项目的长期方向定义，由 Agent 1 负责维护。

它回答：

> 我们到底要做一个什么项目？为什么做？最终希望达到什么效果？

文档 A 不应该记录具体开发步骤，而应该记录项目愿景、范围和原则。

## 内容结构

```md
# 项目概述

## 项目是什么
介绍项目目标和核心价值。

## 为什么做
说明项目背景和解决的问题。

# 用户与使用场景

- 给谁使用
- 解决什么问题
- 核心使用流程

# 功能范围

## 必须实现

项目不可缺少的核心功能。

## 可选功能

未来可能增加，但当前不是重点。

## 明确不做

防止项目无限扩张。

# 技术方向

- 推荐技术栈
- 大致架构
- 技术限制

# 项目原则

例如：

- 简洁优先
- 不进行无意义重构
- 优先保证核心体验

# 当前决策

记录已经确定的重要选择以及原因。

# 未来可能变化

记录暂时无法确定的问题。
```

## 修改规则

Agent 1 可以修改文档 A 的情况：

- 用户产生新的需求
    
- 项目目标发生变化
    
- 经过讨论发现原方向存在根本问题
    

Agent 1 不应该因为某个 Phase 开发失败而直接修改文档 A。

技术问题应该通过 Report → Agent 2 → 修改 Plan 解决。

---

# 文档 B：Development Plan

## 定位

文档 B 是当前阶段的执行路线图，由 Agent 2 负责维护。

它回答：

> 为了实现文档 A 中的目标，现在应该怎么做？

文档 B 会随着项目推进不断变化。

## 内容结构

```md
# 当前目标

说明目前阶段希望完成什么。

# Plan

## 目标

本阶段要解决的问题。

## 技术方案

具体实现思路。

## 为什么这样设计

记录方案选择原因。

## Phase

### Phase 1.0

目标：
实现 xxx。

修改范围：
- xxx
- xxx

实现要求：
- xxx
- xxx

禁止：
- 不修改 xxx
- 不引入 xxx

验证方式：
- 测试通过
- 功能正常

完成条件：
满足以上所有要求。

状态：
completed / running / pending
```

---

# Phase：执行合同

Phase 不是简单的 Todo，而是 Agent 2 给 Agent 3 的执行合同。

一个完整 Phase 应包含：

- 目标：这一次要完成什么
    
- 背景：为什么需要做
    
- 修改范围：允许修改哪些内容
    
- 实现要求：必须满足什么
    
- 禁止事项：明确不要做什么
    
- 验证方式：如何判断完成
    
- 完成标准：什么时候算结束
    

其中「禁止事项」非常重要。

例如：

```md
禁止：

- 不修改数据库结构
- 不引入新的依赖
- 不重构无关模块
- 不修改其他功能
```

它可以避免 Agent 在执行过程中无限扩大任务范围。

# Report：实际结果记录

## 定位

Report 由 Agent 4 生成，用于记录 Phase 执行后的真实情况。

它回答：

> 实际发生了什么？结果如何？下一步应该怎么办？

Report 不是开发日志，而是给 Agent 2 重新规划使用的状态信息。

## 内容结构

```md
# Phase Report

## 1. 本阶段目标

原计划希望完成什么。

## 2. 实际完成情况

实际完成了哪些内容。

## 3. 与计划的偏差

是否按照原计划执行。

如果发生变化：

- 为什么变化
- 如何处理

## 4. 技术发现

开发过程中发现的新问题。

## 5. 遗留问题

当前没有解决的问题。

## 6. 验收结果

### Agent 4 验收

代码逻辑：
代码规范：
架构合理性：

### 用户验收

功能体验：
交互体验：
视觉效果：

## 7. 下一阶段建议

- 是否继续当前方向
- 是否需要修改计划
- 是否新增修复 Phase
```

# Agent 职责与权限

|Agent|负责|不应该做|
|---|---|---|
|Agent 1|修改文档 A，确定项目方向|修改代码、制定详细 Phase|
|Agent 2|修改文档 B，制定 Plan 和 Phase|直接开发代码|
|Agent 3|修改代码，实现 Phase|修改项目目标、随意改变需求|
|Agent 4|验收代码，生成 Report|修改代码、修改 Plan|

---

# Phase 版本规则

采用版本化管理：

## X.0

代表正常开发阶段。

例如：

Phase 1.0：  
实现用户注册功能。

## X.1 / X.2

代表针对当前阶段的修复。

例如：

Phase 1.0 完成后：

- 发现密码校验问题
    
- 创建 Phase 1.1 修复
    

修复完成：

- 进入 Phase 2.0
    

因此：

- 同一个大版本内的 X.x 表示修复和完善
    
- 新的 X.0 表示进入新的开发目标

# 工作循环

完整流程：

```text
Agent 1
↓
文档 A（项目方向）
↓
Agent 2
↓
文档 B（开发计划）
↓
Agent 3
↓
完成一个 Phase
↓
Agent 4
↓
生成 Report
↓
Agent 2 阅读 Report
↓
重新规划
↓
进入下一 Phase
```

如果验收失败：

```text
Phase 1.0
↓
发现问题
↓
Phase 1.1 Fix
↓
重新验收
```

如果验收通过：

```text
Phase 1.0
↓
优化计划
↓
Phase 2.0
```

# 最终原则

这个工作流的核心不是追求单个 Agent 的能力最大化，而是通过职责分离降低复杂度。

优秀的项目流程应该是：

- 文档 A 保持方向稳定
    
- 文档 B 持续调整计划
    
- Phase 限制单次任务范围
    
- Agent 3 专注执行
    
- Agent 4 专注判断
    
- Agent 2 根据反馈重新决策
    

最终形成：

**Vision → Plan → Execution → Review → Re-plan**

的持续迭代闭环。
