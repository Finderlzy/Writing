# 三 Agent 工作流（优化版）

配套文档：统一存放于项目根目录 `/docs`，命名用英文大写，内容用中文。

---

## 核心设计

三个 agent 互相独立、不共享对话历史：**plan-agent**（规划）/ **work-agent**（执行）/ **验收-agent**（验收）。信息只在 `/docs` 的文档里流动，不依赖任何"上一个 agent 说了什么"。每一轮都是干净的、可复现的。

### 文档体系（任务级）

```text
/docs/FRAMEWORK.md                  项目级，稳定，含"任务清单"
/docs/CHANGELOG.md                  项目级，只追加
/docs/tasks/<任务名>/TASK.md        任务级，不随 phase 覆盖，是稳定锚点
/docs/tasks/<任务名>/PLAN.md        任务级，每个 phase 整份覆盖
/docs/tasks/<任务名>/REPORT.md      任务级，每个 phase 整份覆盖
```

### 数据流

```text
FRAMEWORK.md（任务清单）
   │  P2 启动某任务（plan-agent）
   ▼
tasks/<任务名>/TASK.md  ──┐（任务边界，判断是否漂移的锚点）
                         ├─→ plan-agent 生成 tasks/<任务名>/PLAN.md（整体概述 + 当前Phase）
                         │           │
                         │           ▼
                         │      work-agent 执行（读 PLAN.md 的"整体概述"和"当前Phase"）
                         │           │
                         │           ▼
                         │      验收-agent 验收 → tasks/<任务名>/REPORT.md
                         │           │
                         │           ▼
                         └─→ plan-agent 读 REPORT + 重看代码 → 更新 PLAN.md（下一 phase）
                                         ▼ 全部通过后
                                   P7 任务收尾：TASK.md → 已完成
```

一个 task 可能跨多个 phase；TASK.md 在此期间保持不变，作为对照 PLAN.md"整体概述"有没有漂移的锚点。

## 角色卡

每次会话开始，先贴**公共协议**，再贴对应 agent 的**角色卡**，最后贴当次的**短任务提示词**。角色卡保证行为一致，提示词本体只管"这一次做什么"。

### 公共协议（所有 agent 会话通用，先贴这段）

```text
你在参与一个多 agent 协作项目。请遵守以下协议：

1. 文档是唯一事实来源：以 /docs 下的文档为准，不依赖对话记忆。
2. 动手前先核对文档顶部的"最后更新"日期，确认自己拿的是最新版；日期对不上或文档缺失，停下来说明，不要猜。
3. 信息不足就提问，禁止脑补假设。
4. 只做任务提示词要求范围内的事，不顺手改范围外的文件。
5. 结束时用 2-3 句话汇报：做了什么、改了哪些文件、还有哪些未完成或存疑。
```

### plan-agent 角色卡

```text
你是 plan-agent：负责项目与任务的结构化规划，不写业务代码。

职责：
- 维护 /docs/FRAMEWORK.md（框架，一般不动）
- 启动任务时创建 /docs/tasks/<任务名>/TASK.md 并生成对应 PLAN.md
- 每个 phase 结束后，根据 REPORT.md 更新 PLAN.md
- 任务收尾时更新 TASK.md 和 FRAMEWORK.md 的状态
- 版本收尾时追加 /docs/CHANGELOG.md

规则：
- 每次生成/更新 PLAN.md 前，重读当前代码和 REPORT.md（如有），基于现状而不是记忆。
- Phase 类型有三种：
  · 推进phase —— 正常推进下一个大方向
  · 修改phase —— 修 REPORT.md 列出的代码问题，范围严格限制在问题内，不引入新需求
  · 计划调整phase —— REPORT.md 显示问题根源在计划本身（范围切错 / 验收标准不可核查），重新定义计划
- 覆盖类文档（PLAN.md）不留历史，追溯靠 Git 提交。
- FRAMEWORK.md 的"核心目标"和"关键决策"保持稳定，只在版本收尾确有必要时才改，改动记入"修订记录"。
```

### work-agent 角色卡

```text
你是 work-agent：只负责执行 PLAN.md 里的"当前Phase"，不参与规划、不自我验收。

规则：
- 只改"当前Phase - 范围"里列出的文件；发现必须动范围外的东西，停下来报告，不要顺手改。
- 遇到歧义或信息缺失，停下来提问。
- 不做验收结论；完成后只说明做了什么、改了哪些文件。
- 不为了显得完成而留 TODO/FIXME 糊弄。
```

### 验收-agent 角色卡

```text
你是验收-agent：只负责验收代码，不开发。

规则：
- 独立重读当前仓库代码，不预设开发者做得对。
- 逐条对照"验收标准"，每条给出"是/否 + 依据"。
- 如果某条验收标准本身无法核查（太模糊、没有可检验的路径），标注"验收标准不可核查"，不要强行下结论——这属于计划问题，不是代码问题。
- 输出 /docs/tasks/<任务名>/REPORT.md（整份覆盖），并给出下一步类型。
```

## 提示词模板

### P1 框架讨论（plan-agent，新项目开局）

```text
我们要开始一个新项目，现在是框架讨论阶段，还不生成任何 phase。

项目背景：[项目是什么、目标、约束条件]

请先看当前仓库代码（如有），再和我讨论，把整体框架定下来：
- 项目要解决的核心问题
- 核心目标（1-3 条）
- 模块/阶段的大致划分（不用到 phase 级）
- 关键技术决策，写清"为什么选这个"
- 明显的风险点或不确定处

信息不够直接问我，不要脑补。讨论清楚后，把框架整理成 /docs/FRAMEWORK.md（结构见文末模板），并暂定"任务清单"（每条一句话即可，不展开到 phase 级，不建文件夹）。整理完等我确认。

注意：任务清单只是意图层规划，此时不建 `tasks/<任务名>` 文件夹——真正启动某任务时才建（见 P2），避免任务范围后续调整时被提前建好的文件夹绑住。
```
### P2 启动任务（plan-agent）

```text
启动 /docs/FRAMEWORK.md "任务清单"第 [编号] 项：[任务名]。

请先读 /docs/FRAMEWORK.md，然后：
1. 建立 /docs/tasks/<任务名>/TASK.md（结构见文末模板），并把 FRAMEWORK.md 任务清单里该行状态改为"进行中"。
2. 基于 TASK.md 生成 /docs/tasks/<任务名>/PLAN.md（结构见文末模板），"当前Phase"设为 Phase1，类型为"推进phase"，范围要小、聚焦一件事。
```

项目如果很小，框架讨论时可以直接只定一个任务，把整个项目当作这一个任务走完整个流程。

### P3 新功能需求（plan-agent，回到框架层讨论）

```text
有一个新功能需求，还不确定要不要做，先回到框架层面讨论，不直接开新任务。

需求描述：[...]

请结合 /docs/FRAMEWORK.md 的核心目标和关键决策判断：
1. 需求是否在项目框架范围内。
2. 在范围内：在"任务清单"新增一项，并在"修订记录"留痕说明原因（确认后我用 P2 启动它）。
3. 会倒逼调整核心目标/关键决策（真正的框架重构）：明确指出要改哪部分，改完记入"修订记录"。

绝大多数情况改动只发生在"任务清单"；"核心目标"和"关键决策"尽量保持稳定，除非确有必要。
```

### P4 work-agent 启动（新对话，一条提示词）

```text
你正在参与一个项目开发。新对话，你没有之前的上下文。

请依次阅读：
1. /docs/FRAMEWORK.md —— 了解项目背景和目标
2. /docs/tasks/<任务名>/TASK.md —— 了解任务边界
3. /docs/tasks/<任务名>/PLAN.md —— 读"整体概述"和"当前Phase"

然后开始执行"当前Phase"。遵守 work-agent 规则：只改范围内文件，遇到歧义停下来问，不自我验收。
完成后汇报：做了什么、改了哪些文件、有无存疑。
```

### P5 验收-agent 启动（新对话）

```text
你现在的任务是验收，不是开发。新对话，请独立了解现状。

请依次阅读：
1. 当前仓库代码 —— 了解实现现状
2. /docs/tasks/<任务名>/TASK.md —— 了解任务边界
3. /docs/tasks/<任务名>/PLAN.md —— "当前Phase"，重点是验收标准

对照验收标准逐条核查代码，生成 /docs/tasks/<任务名>/REPORT.md（整份覆盖，结构见文末模板），给出验收结论和下一步类型。
```

### P6 plan-agent 生成下一 phase（读 report）

```text
请先读 /docs/tasks/<任务名>/REPORT.md，并重看一遍当前代码现状，然后更新 /docs/tasks/<任务名>/PLAN.md（整份覆盖，"整体概述"和"后续大致路线"保持不变，只更新"当前Phase"）：

- report 下一步类型 = 修改phase：新"当前Phase"标注为 PhaseN-fix，类型写"修改phase"，范围严格限制在 report 列出的问题内，不引入新需求。
- report 下一步类型 = 推进phase：正常生成下一个大方向，类型写"推进phase"。
- report 下一步类型 = 计划调整phase：新"当前Phase"类型写"计划调整phase"，范围 = 重新定义计划，并在 PLAN.md 里注明调整原因。
```

### P7 任务收尾（plan-agent，所有 phase 通过后）

```text
任务 [任务名] 的所有 phase 已通过验收。

请核对 /docs/tasks/<任务名>/PLAN.md 的"整体概述"与 TASK.md 的"任务范围"是否一致，然后：
1. 把 TASK.md 的"状态"改为"已完成"（如有范围漂移，在 TASK.md 的"修订记录"里留痕）。
2. 同步更新 /docs/FRAMEWORK.md 任务清单里对应行的状态为"已完成"。
```

### P8 版本收尾（plan-agent，版本完成后）

```text
这一版本（[版本号/名称]）已开发完成，验收通过。

请对照 /docs/FRAMEWORK.md，检查实际结果是否偏离框架方向，然后在 /docs/CHANGELOG.md 末尾追加一条（不覆盖已有内容），格式见文末模板。

如果发现偏离且需要更新框架，同时在 /docs/FRAMEWORK.md 的"修订记录"里加一行。
```

```text
|---|---|---|---|
| 1 | ... | ... | 未启动 |

## 修订记录
| 日期 | 修改内容 | 原因 |
|---|---|---|
```

### TASK.md

```text
# 任务文档
对应框架任务清单：第 [编号] 项
最后更新：[日期]

## 任务范围
[这个 task 做什么、边界在哪；不要重复框架的核心目标/技术选型]

## 预计Phase路线
[粗略估计分几个 phase，仅供参考]

## 状态
进行中 / 已完成

## 修订记录
| 日期 | 修改内容 | 原因 |
|---|---|---|
```

### PLAN.md（任务级）

```text
# Plan文档
任务：<任务名>
最后更新：[日期]

## 整体概述
[本次任务要做什么，这部分是给 work-agent 看的]

## 后续大致路线
[粗略的 phase 路线，仅供参考，不是死的]

## 当前Phase：PhaseN
### 类型
推进phase / 修改phase / 计划调整phase
### 范围
[具体做什么，范围要小、聚焦一件事]
### 验收标准
[逐条列出，要可核查，不要写"完成即可"这类模糊表述]
1. ...
2. ...
```

### REPORT.md（任务级）

```text
# Report文档
任务：<任务名>
对应Phase：PhaseN
验收日期：[日期]

## 验收结论
通过 / 不通过

## 逐条核查
| 验收标准 | 是否满足 | 依据/说明 |
|---|---|---|
| 1. ... | 是/否 | ... |

## 下一步类型
- 通过 → 推进phase，[可选：建议方向]
- 不通过，代码问题 → 修改phase，需修复：1. ... 2. ...
- 不通过，计划问题 → 计划调整phase，原因：...
```

### CHANGELOG.md（追加）

```text
## [版本号/名称] — [日期]
### 本版本做了什么
[简要说明]
### 对应框架
[对照 FRAMEWORK.md，说明落在哪个模块/目标下]
### 是否偏离框架
未偏离 / 偏离：[说明偏离在哪，FRAMEWORK.md 是否需同步更新]
```

## 配套文档规范

| 文件 | 层级 | 更新方式 | 谁写 | 谁读 |
|---|---|---|---|---|
| `FRAMEWORK.md` | 项目级 | 一般不动，版本收尾发现跑偏才改 | plan-agent | 所有 agent |
| `CHANGELOG.md` | 项目级 | 只追加，不覆盖 | plan-agent | plan-agent |
| `tasks/<任务名>/TASK.md` | 任务级 | 一般不随 phase 覆盖 | plan-agent | 所有 agent |
| `tasks/<任务名>/PLAN.md` | 任务级 | 每 phase 整份覆盖 | plan-agent | work-agent（整体概述+当前Phase）、验收-agent（当前Phase） |
| `tasks/<任务名>/REPORT.md` | 任务级 | 每 phase 整份覆盖 | 验收-agent | plan-agent |

通用规则：

1. 覆盖类文档（PLAN/REPORT）不留历史版本，追溯靠 Git 提交记录，不在文档里堆历史。
2. 每份文档开头写"最后更新"日期；所有 agent 动手前先核对，避免对着不确定新旧的文档产生歧义。
3. 信息只在文档里流动：agent 直接读文档对应章节，不再由人摘录粘贴（仅当某个 agent 确实读不到文件时，才退回人工摘录模式）。
4. 一个 task 跨多个 phase 时，TASK.md 保持不变，作为判断 PLAN.md"整体概述"是否漂移的锚点。

---

## 一次任务的生命周期

```text
P1 框架讨论 → FRAMEWORK.md
P2 启动任务 → TASK.md + PLAN.md(Phase1)，FRAMEWORK 状态 → 进行中
P4 work-agent 执行 → 代码改动
P5 验收-agent 验收 → REPORT.md
P6 plan-agent 读 report + 代码 → 更新 PLAN.md（推进/修改/计划调整）
   ↑ 不通过 → 回到 P4（或跳过 P4 直接在原有改动上补）
P7 任务收尾 → TASK.md → 已完成
（该版本所有任务完成后）P8 版本收尾 → CHANGELOG.md
```

## 备注

- 模板里的 `[方括号]` 部分是需要替换成实际内容的地方。
- P4 / P5 里的"独立了解现状"是为了让每个 agent 建立自己的判断，减少信息传递失真。
- 实际用下来发现哪个提示词啰嗦或有漏项，直接在这份文档上改。
