# 项目驱动学习的笔记结构

## 为什么项目笔记容易读起来“不舒服”

项目驱动学习常常按真实发生顺序推进：先配配置文件，再写一个函数，遇到新 API 后岔出去理解语法，回来继续调试，随后又发现另一个基础概念。

这个过程很适合探索，却不适合直接成为最终笔记结构。

如果完全按时间记录，笔记会变成：

`今天改了什么 → 遇到哪个函数 → 查了什么 → 又改了什么`

每一段单独看可能都正确，但读完只记得若干函数，脑中没有系统怎样运行的整体模型。

问题不是内容太多，而是把三种不同性质的信息写在了同一层：

- 项目怎样一步步实现；
- 系统中的数据和调用怎样流动；
- 某个可复用概念本身是什么。

## 第一条轴：项目主线与概念笔记分开

### 项目主线记录“这个系统怎样工作”

项目主线应该围绕目标、模块和数据流组织，而不是围绕今天碰到的函数组织。

以一个给 AI 网页输入增加自定义指令的 Chrome 扩展为例，主线可以先给出整体流程：

`popup 输入指令 → chrome.storage → content script 读取 → 用户发送问题 → 拼接指令与问题 → 修改输入框 → 页面正常发送`

之后再按流程解释每个模块。这样 `setInputValue()`、`handleSend()` 之类函数只是流程中的工具，不会反过来成为整篇笔记的骨架。

项目主线适合记录：

- 项目要解决的问题；
- 模块职责；
- 数据流与调用关系；
- 关键设计选择及原因；
- 当前项目特有的约束和案例；
- 指向相关概念笔记的链接。

### 概念笔记记录“这个东西本身是什么”

概念笔记应该能脱离当前项目独立存在。

例如在项目里遇到：

```js
document.addEventListener("click", handler, true);
```

项目主线只需解释为什么这里要监听点击，以及它在发送流程中的位置，然后链接到：

- `[[DOM 事件监听]]`
- `[[事件传播]]`
- `[[事件捕获]]`

概念笔记再解释机制、最小示例、常见误解和不同项目中的案例。

一个实用判断是：

> 这个知识离开当前项目以后仍然有意义，而且以后很可能再次出现吗？

如果答案是肯定的，适合形成概念笔记。某个通用 API、事件机制或存储机制通常值得保留；某个页面按钮的 CSS 选择器、项目自定义函数名和一次性变量通常留在主线即可。

## 第二条轴：先画系统，再解释局部

即使主线和概念已经分开，项目主线内部仍需要层次。

### 系统层

先回答：

- 系统的目标是什么？
- 有哪些模块？
- 数据从哪里来，到哪里去？
- 一次完整操作经过哪些步骤？

这一层让读者先看到森林。

### 实现层

再进入某个局部：

- 为什么不能直接修改 `input.value`？
- 为什么需要触发 `input` 事件？
- `setter.call(...)` 在这里做了什么？

这一层解释树木。没有系统层，函数会显得彼此孤立；没有实现层，流程图又容易变成没有机制的空壳。

## 对话可以发散，笔记不能照抄发散顺序

聊天的职责是探索。真实学习过程完全可以是：

`主线 → 支线 → 支线中的概念 → 发现没懂 → 补基础 → 回到主线`

没必要为了保持聊天整洁，强行给每个支线开一个新对话。上下文完整时，模型可以直接用当前项目的真实问题解释概念。

但整理笔记时，应该重新组织：

- 项目主线保留最终数据流、关键选择和验证结果；
- 可复用机制抽成概念笔记；
- 探索过程中被推翻的方案只在必要时作为反例；
- 重复的解释合并，不忠实复制聊天顺序。

对话结构和知识结构本来就不应该一模一样。

## 概念笔记的第一个案例从哪里来

概念第一次出现时，最好先用触发它的真实项目问题解释。

例如不要突然背诵“DOM 事件传播分为捕获、目标和冒泡”，而是从当前问题出发：

`为什么监听 document，也能感知用户点击里面的按钮？`

为了回答这个问题，才引出事件如何沿 DOM 树传播。概念因此拥有明确的存在理由。

理解机制后，再补一个最小、通用的例子，帮助它脱离具体项目。以后在新项目再次遇到同一概念，就继续增加新案例，而不是重新创建“另一个项目里的事件捕获”。

## 怎样避免概念笔记碎成渣

主线拆得不够会变成流水账，拆得太过又会出现几百篇只有三句话的孤立笔记。

不要看到每个函数和属性都立刻建文件。可以先问：

1. 它是否能独立回答一个稳定的问题？
2. 它是否可能在不同项目中重复出现？
3. 目前是否已有相近概念可以容纳它？
4. 单独拆分后，是否比作为现有概念的一个小节更容易理解？

第一次只理解了 40%，概念笔记就先写 40%。保留“尚未理解”的问题，等下次项目遇到时继续补充。概念笔记不是百科词条，而是逐渐演化的个人理解。

## 领域标签与主题标签不要混用

历史对话里还出现了另一种常见混乱：想用标签表示宏观领域，模型却自动提取了具体主题。

- 领域：编程、写作、数学、二次元。
- 主题：神经网络、事件捕获、角色动机、三段式结构。

领域适合回答“这篇大体属于哪一类”，主题适合回答“这篇具体讲了什么”。如果希望 AI 自动分类，必须明确它要做的是领域归类还是主题提取，并优先复用已有分类，否则标签会持续发散。

文件夹、链接和标签解决的是不同问题：

- 文件夹提供主要归属；
- 链接建立跨主线的知识关系；
- 标签提供额外检索维度。

不要让一种工具同时承担全部职责。

## 一份项目学习笔记的推荐骨架

```text
# 项目或阶段目标

## 要解决的问题

## 整体结构
- 模块
- 数据流
- 调用关系

## 1. 第一个流程环节
- 为什么需要
- 输入与输出
- 关键实现
- 验证结果

## 2. 第二个流程环节
...

## 关键设计选择

## 相关概念
- [[概念 A]]
- [[概念 B]]

## 仍未解决的问题
```

这个骨架不是固定模板。真正的原则是：先让读者看懂系统为何存在、怎样流动，再把函数和语法挂到正确位置。

## 最后留下的原则

聊天负责探索，主线笔记负责重建系统，概念笔记负责积累可复用理解。

不要按“今天学了哪些函数”组织项目笔记，而要按“系统怎样工作”组织；不要把所有支线塞进主线，而要让可复用概念独立生长，再通过链接回到真实案例。
