# Obsidian 到 MkDocs 兼容层设计

日期：2026-08-22
状态：已确认

## 背景

本站以 Obsidian 仓库中的 Markdown 笔记作为内容源，通过 MkDocs Material 构建并部署到 GitHub Pages。当前使用 `mkdocs-publisher` 的 `pub-obsidian` 插件兼容部分 Obsidian 语法，但已经确认存在以下问题：

- Callout 被转换成 MkDocs Admonition 语法后，没有被继续渲染；
- 紧贴中文的 `==高亮==` 部分保留为原始文本；
- Obsidian 可以识别的宽松列表在 Python Markdown 中变成普通段落；
- 同一行的多个普通双链可能被插件错误合并；
- Obsidian 的全库短链接无法稳定解析跨目录目标；
- Obsidian 块 ID 没有生成真正的 HTML 锚点；
- 缺失、歧义和无效锚点不会阻止现有部署流程。

逐篇修改笔记只能处理当前症状，之后新写的 Obsidian 笔记仍会产生同类问题。

## 设计目标

1. `docs/` 中的 Obsidian 原生 Markdown 是唯一事实来源。
2. 作者不需要为了网站手工改写笔记，也不需要点击额外的转换按钮。
3. 构建过程自动把受支持的 Obsidian 语法转换为 MkDocs 可稳定渲染的 Markdown。
4. 转换过程不得修改 `docs/` 中的原始文件。
5. 缺失、歧义或无效的站内引用必须阻止发布，并指向原始文件位置。
6. 本地构建与 GitHub Actions 必须使用同一入口和相同依赖版本。

## 非目标

首期不实现完整的 Obsidian，也不支持当前仓库没有实际需求的功能：

- Dataview 查询；
- Canvas；
- 标签关系图；
- Obsidian 插件私有语法；
- Markdown 页面内容嵌入 `![[另一篇笔记]]`；
- 外部链接的联网可用性检查。

这些能力只有在仓库出现真实使用需求时才单独设计和实现。

## 方案决策

采用独立的构建期兼容层，保留 MkDocs Material、现有导航、搜索和 GitHub Pages 部署。

不采用以下方案：

- 不继续通过零散配置和逐篇手改维持兼容，因为这会让网站格式反向污染内容源；
- 不制作 Obsidian 中的“一键转换”按钮，因为按钮可能漏点，并会产生原文与转换结果两种内容状态；
- 暂不迁移 Quartz 等其他生成器，因为迁移主题、导航、搜索和部署的成本超过当前需求。

兼容层稳定后移除 `pub-obsidian`，避免转换后的内容被插件二次处理。

## 总体架构

```text
docs/ 原始 Obsidian 笔记（只读）
  ↓
Vault 索引器
  ↓
结构化语法解析器 + 链接解析器
  ↓
.cache/converted-docs/ 临时标准 Markdown
  ↓
MkDocs 严格构建
  ↓
生成 HTML 的站内链接与锚点复检
  ↓
site/
```

统一构建入口负责依次调用全部阶段。建议的用户入口为：

```text
python tools/build_site.py
```

具体文件划分在实施计划中确定，但解析、索引、转换、诊断和构建编排必须保持独立，不能集中在一个大型脚本中。

## 组件职责

### Vault 索引器

扫描 `docs/`，为 Markdown 文件和附件建立规范化索引。索引至少包含：

- 相对于 `docs/` 的完整路径；
- 不带扩展名的路径；
- 文件名；
- 页面标题及其生成后的 slug；
- Obsidian 块 ID；
- 附件路径。

索引器只提供查询能力，不转换正文。它必须保留同名目标的全部候选项，不能用“最后一个覆盖前一个”的方式隐藏歧义。

标题 slug 必须调用与最终 MkDocs 渲染相同的生成规则，不能在兼容层中自行实现另一套近似算法。

### 结构化语法解析器

解析器先识别 YAML 属性区、围栏代码块、行内代码和普通正文，再只处理正文中的 Obsidian 语法。它不能用一个覆盖全文的正则表达式完成转换，以免重现同行双链被吞并或代码示例被误改的问题。

解析结果需要保留源文件、行号和列号，使后续诊断能够返回原始位置。

### 链接解析器

页面链接按固定优先级解析：

1. 链接中写明的显式相对路径；
2. 当前笔记所在目录中的目标；
3. 全库中名称唯一的目标；
4. 多个候选项时报歧义；
5. 没有候选项时报缺失。

标题引用需要验证标题 slug；块引用需要验证目标页面中的块 ID。附件使用相同原则，但只匹配实际附件文件。

### 转换器

转换器接收解析后的结构和已经解析的目标，不自行搜索文件。首期转换规则如下：

- `[[页面]]` 转换为目标明确的标准 Markdown 链接；
- `[[页面|文字]]` 保留显示文字；
- `[[页面#标题]]` 转换并验证标题锚点；
- `[[页面#^block-id]]` 转换并验证块锚点；
- `![[附件]]` 转换为标准图片或附件链接；
- `> [!note]` 等受支持 Callout 转换为 MkDocs Admonition；
- `==文字==` 转换为 `<mark>文字</mark>`，不依赖单词边界；
- `^block-id` 转换为真正的 HTML 锚点；
- 仅在临时输出中补齐列表渲染所需的空行和缩进。

YAML 属性区和普通标准 Markdown 原样保留。

### 临时输出层

转换后的目录写入 `.cache/converted-docs/`，保持与 `docs/` 相同的相对结构，并复制构建所需附件。

该目录必须：

- 被 Git 忽略；
- 每次完整重建，不能残留已删除页面；
- 可以在诊断时保留供检查；
- 不得作为内容源被人工编辑。

### 构建包装器

构建包装器是本地和 CI 的唯一入口，依次执行：

1. 清理并创建临时输出；
2. 建立 Vault 索引；
3. 解析、解析链接并转换全部笔记；
4. 检查是否残留未处理的受支持 Obsidian 标记；
5. 对临时内容执行 `mkdocs build --strict`；
6. 检查最终 HTML 中的站内页面、附件和锚点；
7. 成功后保留 `site/` 作为发布产物。

任一阶段失败时返回非零退出码，GitHub Actions 不得继续上传或部署。

构建包装器加载现有 `mkdocs.yml` 后，在进程内把 `docs_dir` 覆盖为 `.cache/converted-docs/`，再调用 MkDocs。不得修改仓库中的 `mkdocs.yml` 来回切换目录，也不得让 MkDocs 在该入口中重新读取原始 `docs/`。

## 错误处理

以下问题必须阻止构建：

- 站内页面不存在；
- 页面名称匹配到多个候选项；
- 图片或附件不存在；
- 标题或块 ID 不存在；
- 同一页面存在重复块 ID；
- 双链、嵌入或 Callout 语法未闭合；
- 转换后正文仍残留未处理的双链、嵌入或 Callout；
- MkDocs 严格构建失败；
- 最终 HTML 存在无效站内地址或锚点。

诊断必须使用统一格式，并指向原始文件，例如：

```text
docs/碎碎念/学习/⭐学习流.md:81:6
[E_LINK_AMBIGUOUS] “学习方法”匹配到 2 个页面：
- 碎碎念/学习/学习方法.md
- 临时笔记/学习方法.md
请在 Obsidian 链接中写明路径。
```

以下情况不阻止构建：

- 外部网站暂时无法访问；
- 代码块或行内代码中的 Obsidian 语法示例；
- 不会被兼容层误解释的普通文本。

## 支持范围

首期支持当前仓库已经实际使用的能力：

- 页面双链、别名、相对路径和全库唯一短名称；
- 标题引用与块引用；
- 图片、PDF 等附件；
- `note`、`question`、`warning`、`example` Callout；
- Obsidian 高亮；
- 宽松列表；
- YAML 属性区。

出现新的 Obsidian 专有语法时，默认行为是保持原文；只有当它可能被错误渲染或造成静默数据损失时才应报错。新增支持必须同时增加解析、转换和验收测试。

## 测试设计

### 解析单元测试

每种语法使用最小输入测试，并覆盖：

- 中文字符紧贴高亮边界；
- 同一行多个双链；
- 别名和路径中的空格、中文及标点；
- YAML、代码块和行内代码隔离；
- 未闭合语法；
- Callout 与普通引用的区别；
- 列表与前后段落的边界。

### 链接解析测试

覆盖显式相对路径、当前目录、全库唯一名称、同名歧义、目标缺失、标题存在与缺失、块 ID 存在与缺失、重复块 ID，以及附件解析。

### 黄金文件测试

选择包含多种真实语法的现有笔记作为固定输入，保存预期转换结果。依赖升级或解析规则调整后，黄金文件的变化必须被明确审查。

### 仓库级构建测试

对完整 `docs/` 执行转换和严格构建，确保真实内容不会触发只在组合情况下出现的问题。

### HTML 验收测试

遍历 `site/` 中生成的 HTML，检查：

- 所有站内页面目标存在；
- 图片和附件存在；
- URL 中的片段锚点存在；
- 正文中不残留未处理的 Obsidian 标记；
- 当前已知问题页面的 Callout、高亮、列表和链接结构正确。

### 源文件不变性测试

构建前后比较 `docs/` 文件哈希，确认构建过程没有修改内容源。Git 工作区中用户已有的修改也不能被构建脚本覆盖或暂存。

## CI 与依赖

GitHub Actions 不再直接调用 `mkdocs build`，而是调用统一构建入口。只有入口成功后才能上传 Pages artifact。

Python、MkDocs Material、Markdown 扩展及兼容层依赖必须锁定版本。本地安装与 CI 安装使用同一依赖声明，依赖升级作为独立改动验证，不能在普通内容发布时隐式升级。

## 验收标准

实现完成后必须同时满足：

1. `docs/` 构建前后的文件哈希一致；
2. 当前仓库使用的首期语法全部正确转换；
3. 站内页面、附件和锚点不存在无效目标；
4. 正文中不存在未处理的受支持 Obsidian 标记；
5. 本地与 CI 使用相同构建命令；
6. 任一确定性错误都能以原始路径和位置阻止发布；
7. 当前已确认的 Callout、高亮、宽松列表、同行双链、跨目录短链和块引用问题均有回归测试；
8. 移除 `pub-obsidian` 后没有功能回退。

## 迁移顺序

实施应按以下顺序推进：

1. 为当前故障建立失败测试和真实笔记夹具；
2. 实现 Vault 索引和确定性链接解析；
3. 实现结构化解析及首期语法转换；
4. 接入临时输出和 MkDocs 严格构建；
5. 增加最终 HTML 验收；
6. 将本地与 CI 切换到统一入口；
7. 移除 `pub-obsidian`；
8. 使用完整仓库和关键页面进行回归验收。

迁移期间不批量改写现有笔记。真正缺失、歧义或本身写坏的引用由构建诊断列出，再由作者决定补页面、写明路径或删除链接。
